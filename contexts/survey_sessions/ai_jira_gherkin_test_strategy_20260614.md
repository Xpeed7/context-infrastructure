# AI 生成 Jira 文本用例与 Gherkin 自动化用例方案调研

日期：2026-06-14
模式：Internal memo
主题：基于需求文档与开发文档，生成 Jira 文本测试用例，并进一步生成 Gherkin Style 自动化测试用例

## 1. 问题定义

这件事表面上看是一个生成任务，实际是一个分层编译任务。输入不是代码，而是多源语义不完整的业务文档；输出也不是一层，而是两层不同目的的测试资产。

第一层输出是 Jira 文本用例。它服务的是测试设计、评审、追踪和协作，重点是覆盖范围、业务可读性、风险表达和执行指引。

第二层输出是 Gherkin Style 自动化测试用例。它服务的是自动化执行和持续回归，重点是步骤可执行、前置条件稳定、断言可观测、数据可控。

所以真正的问题不是“能不能让 AI 生成用例”，而是“如何把文档中的业务意图、系统行为、约束条件和风险点，稳定地编译成两类不同粒度的测试资产，并控制语义损耗”。

## 2. 推荐结论

如果目标是落地，推荐把方案定义成一个双阶段生成系统，而不是一个大 prompt。

第一阶段，生成 Jira 文本用例。目标是把需求理解、场景分解、优先级判断和覆盖范围表达清楚。

第二阶段，从已评审或半评审通过的 Jira 文本用例继续生成 Gherkin。目标不是重新理解业务，而是把已有测试意图翻译成自动化可执行表达。

这个分层很重要。直接从需求文档生成 Gherkin，最大的风险不是语言质量，而是可执行性幻觉。模型会写出看起来像自动化脚本设计的句子，但其中一半步骤没有稳定数据前提，一半断言没有可观测接口，另一半依赖隐含业务规则。Jira 层是业务测试设计层，Gherkin 层是执行契约层，中间必须有一道质量闸门。

## 3. 为什么这个方向成立

这个方向成立，不是因为 LLM 更会写用例，而是因为它在三个环节里有明显优势。

第一，信息压缩。需求文档、接口文档、页面说明、流程图、PRD、技术设计文档常常分散、重复且口径不一致。模型擅长在这些异构文本里抽取实体、角色、状态、规则和异常流。

第二，模式归纳。高质量测试用例本身有稳定结构：前置条件、输入、动作、预期结果、边界条件、异常路径、优先级、标签。模型能把散乱信息映射到这类结构化模板。

第三，文本变换。Jira 文本用例和 Gherkin 用例都属于强格式文本。只要中间语义层设计好，LLM 非常适合承担“语义到模板”的转换器角色。

## 4. 真正难点

### 4.1 输入文档不是测试友好的

多数需求文档不是为测试生成准备的。常见问题有：

- 业务流程说了主链路，没说异常链路
- 需求写了页面动作，没写后端状态变化
- 开发文档写了接口字段，没写业务约束
- 不同文档对同一概念命名不一致
- 需求粒度和实现粒度错位

如果不先做中间抽取，模型只能靠补全。补全能力越强，幻觉风险越大。

### 4.2 Jira 用例和 Gherkin 用例的目标函数不同

Jira 用例追求“业务表达完整”。它允许自然语言，可以保留一定模糊度，适合人工评审。

Gherkin 用例追求“行为可执行”。它需要明确 actor、system state、action、observable result。很多 Jira 文本用例看起来没问题，但无法直接落成 Gherkin，比如：

- “验证用户可正常提交订单”
- “验证库存不足时有合理提示”
- “验证权限控制符合预期”

这些句子对人类足够，对自动化不够。Gherkin 需要把“正常”“合理”“符合预期”展开成具体条件与断言。

### 4.3 自动化的瓶颈不在写场景，而在写约束

AI 最容易生成的是 happy path 场景。真正稀缺的是下面这些信息：

- 数据准备方式
- 环境依赖
- 权限角色
- 时间条件
- 外部依赖 mock 规则
- 断言采集点
- 清理与回滚策略

没有这些，Gherkin 只是一种看起来专业的自然语言，不是可执行测试资产。

## 5. 建议的系统架构

推荐把链路拆成六层。

### 5.1 文档摄取层

输入源至少包括：

- PRD / 需求文档
- 技术设计文档
- API 文档
- 页面原型或交互说明
- 历史缺陷单
- 现有回归用例

这个阶段不要直接生成用例，先统一切分和标注。建议给每段文本加 metadata：

- 来源类型
- 模块
- 版本
- 业务对象
- 功能点
- 风险标签

如果未来要提高准确率，这层比 prompt 更重要。因为后续所有可追溯性、增量更新、变更影响分析，都依赖这个文档索引。

### 5.2 语义抽取层

这一层是整个方案的核心。建议先从文档中抽出一个测试中间表示，而不是直接出 Jira case。

推荐的中间 schema 至少包含：

- `feature`: 功能点
- `business_goal`: 业务目标
- `actors`: 角色
- `preconditions`: 前置条件
- `main_flow`: 主流程
- `alternative_flows`: 分支流程
- `exception_flows`: 异常流程
- `business_rules`: 业务规则
- `state_transitions`: 状态变化
- `testable_assertions`: 可验证断言
- `dependencies`: 外部依赖
- `test_data_needs`: 测试数据需求
- `risk_notes`: 风险说明
- `source_trace`: 来源段落引用

这一步做对了，后面只是不同模板渲染。做错了，后面生成再漂亮都只是包装错误理解。

### 5.3 测试设计层

这里不应该让模型“自由发挥”，而应该让它按测试设计框架产出候选场景。建议至少覆盖五类：

- 主流程
- 参数边界
- 权限与角色
- 状态迁移
- 异常与降级

如果业务强依赖接口与数据，还应补：

- 幂等性
- 并发冲突
- 重试与超时
- 跨系统一致性

这一层的输出应该是场景卡片，而不是最终 Jira 用例。

### 5.4 Jira 文本用例生成层

建议 Jira case 模板至少包含：

- 用例标题
- 模块 / Feature
- 优先级
- 前置条件
- 测试步骤
- 预期结果
- 测试数据
- 标签
- 来源追踪
- 自动化候选标记

这里要强调一点：不是所有 Jira case 都应该自动进入 Gherkin。需要增加一个字段：`automation_candidate = yes/no/partial`。

判断逻辑可以是：

- `yes`：前置条件清晰、步骤稳定、断言明确、环境可控
- `partial`：主链路可自动化，但异常路径依赖外部系统或复杂数据
- `no`：探索性、视觉性、策略性、一次性验证类用例

### 5.5 Gherkin 生成层

Gherkin 建议不要直接从原文档生成，而是从 Jira case + 中间 schema 联合生成。

推荐模板：

```gherkin
Feature: Order submission

  Background:
    Given a registered buyer account exists
    And the product inventory is 10

  Scenario: Submit order successfully with sufficient inventory
    Given the buyer has added 1 item to the cart
    When the buyer submits the order
    Then the order status should be "SUBMITTED"
    And the inventory should be reduced to 9
    And a payment record should be created
```

生成要求不是“像 Gherkin”，而是满足四条约束：

- 每个 Given 都能映射到可构造环境或数据工厂
- 每个 When 都是单一可执行动作
- 每个 Then 都能映射到明确断言
- 每个 Scenario 都能落到稳定 step definitions

### 5.6 校验与回流层

这是最容易被忽略、但决定方案成败的一层。

至少要有四种校验：

- 格式校验：模板字段是否完整
- 语义校验：步骤与预期是否自洽，是否缺关键条件
- 可执行性校验：Gherkin 中的步骤是否能映射到现有自动化能力
- 追溯性校验：每条用例是否能追到需求源

建议再加一个 AI reviewer，不负责生成，只负责挑错。它专门检查：

- 步骤跳跃
- 前置条件缺失
- 预期结果空泛
- 断言不可观测
- 业务术语混乱
- 场景重复

## 6. 推荐生成策略

### 6.1 不要一步生成，采用“两段生成 + 一段审查”

推荐流程：

1. 文档抽取 -> 中间 schema
2. 中间 schema -> Jira case draft
3. Jira case draft -> AI review / 人工抽检
4. 已通过 Jira case -> Gherkin draft
5. Gherkin draft -> 自动化可执行性 review

这是一个典型的 compiler pipeline，不是单轮 chat。

### 6.2 用规则约束模型，而不是只靠 few-shot

few-shot 对文风有用，对 correctness 不够。应把规则显式写进系统约束里，例如：

- 一个测试步骤只允许一个用户动作
- 一个预期结果必须对应一个可观测结果
- 出现“正常”“正确”“合理”“成功展示”这类词时，必须展开为明确断言
- 每个场景必须声明数据依赖
- 每条用例必须附带来源段落 ID

### 6.3 先做 domain dictionary

如果业务复杂，建议先做术语字典和状态机字典。

术语字典解决命名不一致，比如“订单提交”“下单成功”“创建交易单”到底是不是同一件事。

状态机字典解决状态迁移不一致，比如“待支付”“支付中”“支付成功”“已确认”之间哪些状态可达，哪些事件触发转换。

没有这两层，模型很容易在不同输出里使用不同术语，导致 Jira case 与 Gherkin case 语义漂移。

## 7. Jira 用例设计建议

Jira 层不要只追求数量。推荐把文本用例分成三类。

第一类，业务回归用例。它们直接覆盖核心功能路径，是 Gherkin 的主要来源。

第二类，异常与边界用例。它们中一部分可自动化，一部分只能半自动或保留手工。

第三类，探索性与策略性用例。它们更多用于评审、探索和风险提示，不应强行进入自动化链路。

一个常见误区是要求 AI “尽可能多生成测试用例”。结果往往是大量同义改写和表层组合。更有效的目标是“按风险模型生成最小充分覆盖集”。所以建议对 Jira case 增加以下标签：

- `risk_level`
- `business_criticality`
- `change_frequency`
- `automation_roi`
- `coverage_type`

这样后面才能决定哪些先转自动化，哪些保持手工。

## 8. Gherkin 设计建议

Gherkin 层最怕写成文档化 BDD，而不是工程化 BDD。

推荐原则：

- 一个 Scenario 只覆盖一个核心行为
- 用业务语言写步骤，但保留系统状态可验证性
- Background 只放稳定共性前置，不放会污染场景独立性的初始化
- Then 中尽量包含状态、记录、事件或界面反馈中的至少一种可观测结果

避免以下写法：

- 把多个行为塞进一个长 Scenario
- 把技术实现细节直接写进步骤文本
- 用模糊断言替代具体断言
- 省略测试数据构造条件

如果团队已有 Playwright / Cypress / API automation 体系，Gherkin 模板要反向适配现有 step definitions 风格，而不是重新造一套自然语言 DSL。否则生成量越大，维护成本越高。

## 9. 质量闸门

方案能不能用，不看首轮生成效果，看质量闸门设计。

建议至少设置六个 gate：

1. 文档完整度 gate  
需求文档和开发文档是否足以支持测试生成；如果缺关键信息，先打回补文档，而不是继续猜。

2. 中间 schema 完整度 gate  
是否已经抽出角色、规则、状态、异常流、断言点。

3. Jira 用例可评审性 gate  
测试人员能否读懂并判断覆盖是否合理。

4. Gherkin 可执行性 gate  
自动化工程师能否无大改动接入现有框架。

5. 去重 gate  
多个用例是否只是标题不同、实质重复。

6. 追溯 gate  
每条用例是否能追到需求来源，反向知道为什么存在。

## 10. 评估指标

如果要验证方案，不建议只看“生成速度”。应至少看下面几类指标。

第一，测试设计质量：

- 需求覆盖率
- 异常流覆盖率
- 高风险场景命中率
- 重复用例率
- 人工退回率

第二，自动化可落地性：

- Jira case 到 Gherkin 的可转换率
- Gherkin 到可执行脚本的落地率
- step definitions 复用率
- 数据准备失败率

第三，持续收益：

- 单需求测试设计耗时下降比例
- 回归资产复用率
- 需求变更后的用例更新时延
- 缺陷前移发现率

这些指标里，最关键的不是首轮覆盖率，而是“退回原因结构”。如果大量退回都集中在断言模糊、前置条件缺失、状态理解错误，那么优化重点应该在抽取层，而不是改 prompt。

## 11. 主要风险

### 11.1 文档质量风险

输入文档越模糊，模型越像在补小说。这个风险无法通过更强模型彻底解决，只能通过模板化补充和人工 gate 缓解。

### 11.2 伪覆盖风险

模型会生成看起来覆盖很多的用例，但本质只是把主链路换了几个说法。没有风险模型和去重策略，数量增长会掩盖覆盖贫弱。

### 11.3 可执行性断裂风险

Jira case 看起来合理，不代表 Gherkin 能执行。执行断裂常发生在数据条件、跨系统依赖、异步流程和权限上下文。

### 11.4 维护成本反噬

如果 Gherkin 生成风格不受现有自动化框架约束，很快会出现：

- step 文本高度相似但不可复用
- 一次需求变更要改大量 Scenario
- 自动化团队把生成结果当半成品重写

这时 AI 不是提效，而是在上游制造更多清洗成本。

## 12. 推荐落地路径

### Phase 0：PoC

目标不是全量自动生成，而是验证最小闭环：

- 选 1 个业务模块
- 输入 1 份需求文档 + 1 份开发文档
- 产出 15-30 条 Jira 文本用例
- 其中挑 5-10 条转成 Gherkin
- 由测试负责人和自动化负责人共同评审

PoC 要回答的不是“模型写得像不像”，而是：

- 能否抽出关键业务规则
- Jira case 是否减少测试设计时间
- Gherkin 是否能稳定接入现有自动化框架

### Phase 1：半自动生产

把生成结果定位成 draft，不直接入库。流程是：

- AI 生成
- 测试人员审查
- 通过后写入 Jira
- 自动化候选再进入 Gherkin 转换

这个阶段重点积累两类资产：

- 高质量 few-shot 样本
- 退回原因 taxonomy

### Phase 2：闭环优化

在有足够审查数据后，做两件事：

- 基于退回原因反向优化抽取 schema 和规则
- 把历史通过样本做成检索增强上下文

这时系统会逐步从“通用文本生成”变成“贴合团队测试风格的测试资产编译器”。

## 13. 一个更务实的产品形态

如果把它做成工具，我更建议它长成一个测试设计工作台，而不是一个“输入文档 -> 输出全部用例”的黑盒。

这个工作台至少应该有四个界面能力：

- 文档片段与来源追踪
- 中间 schema 可视化编辑
- Jira 用例草稿评审
- Gherkin 可执行性提示

原因很简单。测试方案不是一次生成，而是多轮判断。把中间层暴露出来，团队才能真正信任系统，也才能定位错误发生在哪一层。

## 14. 最终判断

这个方向值得做，但应该把目标收敛成“用 AI 提升测试设计与自动化编译效率”，而不是“让 AI 自动写完测试”。

最合理的实施顺序是：

第一，先把文档抽取和 Jira case 生成做好，因为这一步离业务价值最近，也最容易建立人类 review 闭环。

第二，再把自动化候选用例转成 Gherkin，并且严格绑定现有测试框架能力，不追求全覆盖。

第三，把审查反馈、执行失败原因和缺陷发现结果回流到 schema 与生成规则中，让系统从一次性生成器演化为团队专属测试知识系统。

这件事的上限不取决于模型多强，而取决于你是否把中间语义层、质量闸门和回流闭环设计清楚。

## 15. 可直接执行的 PoC 建议

如果下周就要开始做，我建议按这个最小闭环启动：

1. 选一个业务模块，准备三类输入：PRD、技术设计、API 文档。
2. 定一个中间 schema，先不用太大，至少包含角色、前置条件、主流程、异常流、规则、断言点、来源追踪。
3. 定 Jira case 模板，增加 `automation_candidate`、`risk_level`、`source_trace` 三个关键字段。
4. 先让 AI 只做 Jira case draft，测试负责人审 20 条，记录退回原因。
5. 从通过的 Jira case 里选 5 条生成 Gherkin，验证是否能接入现有自动化框架。
6. 用一次 PoC 复盘回答三个问题：哪里最常错、哪类 case 最适合自动化、哪些文档字段缺失最致命。

做到这里，这个方向是否值得继续投资源，基本就能判断清楚。
